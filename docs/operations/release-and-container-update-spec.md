# Release And Container Update Spec

This spec defines how Aether versions, container images, production container
updates, database migrations, and rollback records must be managed.

The goal is reproducible releases: a production deployment must be traceable by
Git tag, Git commit SHA, image digest, and database migration/backfill state.

## Release Entry Point

Production release images are built only from explicit Git version tags.

Branch pushes may run CI, tests, or development builds, but must not publish a
production version image. In this repository, `.github/workflows/release.yml`
uses tag-only push triggers for release publishing:

```yaml
on:
  push:
    tags:
      - 'v*'
```

Manual workflow runs are allowed only for validation/dry-run behavior unless the
workflow explicitly receives and validates a release tag context.

## Tag Format

A release tag must use SemVer with a leading `v`:

```text
vMAJOR.MINOR.PATCH
vMAJOR.MINOR.PATCH-alpha.N
vMAJOR.MINOR.PATCH-beta.N
vMAJOR.MINOR.PATCH-rc.N
```

Examples:

```text
v0.7.11
v0.8.0-alpha.1
v0.8.0-beta.2
v0.8.0-rc.1
```

The release workflow must reject tags that do not match:

```regex
^v[0-9]+\.[0-9]+\.[0-9]+(-(alpha|beta|rc)\.[0-9]+)?$
```

Do not use ambiguous release tags such as:

```text
latest
prod
release
v1
v1.2
20260704
```

A published tag must be treated as immutable. Do not delete and recreate a tag to
replace a bad build; publish a new version instead.

## Image Tagging Rules

Every release image must be identifiable by an immutable digest. Mutable tags are
convenience aliases only.

For a stable tag such as `v1.2.3`, the release workflow may publish:

```text
ghcr.io/<owner>/<image>:v1.2.3
ghcr.io/<owner>/<image>:1.2.3
ghcr.io/<owner>/<image>:1.2
ghcr.io/<owner>/<image>:latest
ghcr.io/<owner>/<image>:<git-sha-tag>
```

For a pre-release tag such as `v1.3.0-rc.1`, the release workflow may publish:

```text
ghcr.io/<owner>/<image>:v1.3.0-rc.1
ghcr.io/<owner>/<image>:1.3.0-rc.1
ghcr.io/<owner>/<image>:rc
ghcr.io/<owner>/<image>:<git-sha-tag>
```

Pre-release builds must not update `latest` or minor aliases such as `1.3`.
Only stable releases may update `latest`.

## Build Record Requirements

Every published image build must produce a machine-readable and human-readable
record. The record should be uploaded as workflow artifacts and attached to the
GitHub Release.

Minimum fields:

- release tag
- Git commit SHA
- image repository
- image digest
- full immutable image reference, for example `image@sha256:...`
- image tags generated by the workflow
- workflow run URL
- migration SQL count, latest migration file, and migration manifest SHA256
- backfill SQL count, latest backfill file, and backfill manifest SHA256

In this repository the release workflow emits:

```text
image-build-<tag>.md
image-build-<tag>.json
postgres-migrations.sha256
postgres-backfills.sha256
```

The release image identity for deployment and rollback is the digest, not the
mutable tag.

## Deployment Image Pinning

Production deployment should use an immutable image reference whenever practical:

```text
ghcr.io/<owner>/<image>@sha256:<digest>
```

If deployment uses a mutable tag such as `v1.2.3` or `latest`, the resolved image
digest must still be recorded before and after the update.

For Docker Compose deployments, prefer configuring the app image through an
environment variable such as:

```env
APP_IMAGE=ghcr.io/<owner>/<image>@sha256:<digest>
```

Do not use `latest` as the only record of what is deployed.

## Production Update Safety

Production lifecycle operations must be deliberate. Do not deploy, update,
restart, recreate, stop, remove, pull, or otherwise change production services by
default.

For code or spec changes, limit work to editing files, local validation, commit,
and push. Remote CI/CD builds the artifacts; the operator decides when to update
production.

Examples of production lifecycle commands that require an explicit update or
rollback request:

```text
docker compose pull
docker compose up -d
docker compose restart
docker restart
systemctl restart
kubectl apply
kubectl rollout restart
./update.sh
./deploy.sh
```

Read-only inspection is allowed for diagnosis and release recording.

## Pre-Update Production Snapshot

Before updating production containers, append a snapshot to
`容器更新历史.md` or the deployment's equivalent update history file.

Record at least:

- timestamp and timezone
- compose/project directory
- compose file(s)
- container name, service name, status, health status
- image tag from container config
- image ID and repo digest
- manifest digest when available
- container ID
- container created time and started time
- application version/revision labels when available
- database container version
- Redis/cache container version
- statement that no update/restart/pull has been performed yet

Also record the current database lifecycle state:

- migration table name, for example `public._sqlx_migrations`
- backfill table name, for example `public.schema_backfills`
- latest applied migration and timestamp
- latest applied backfill and timestamp
- failed migration/backfill count
- pending migrations/backfills relative to the checked-out working tree or
  release artifact
- migration/backfill file SHA256 manifest when available

## Update Procedure

A normal production update should follow this order:

1. Confirm the target release tag and image digest from the release build record.
2. Take a pre-update container snapshot.
3. Take a pre-update database migration/backfill snapshot.
4. Create or confirm a database backup if the release may run migrations.
5. Update the configured app image to the target immutable digest or exact tag.
6. Run the minimal production update command approved by the operator.
7. Verify container health checks and application health endpoints.
8. Take a post-update container snapshot.
9. Take a post-update database migration/backfill snapshot.
10. Record any migrations/backfills newly applied during the update.
11. Record the rollback image digest and any rollback constraints.

Database and cache base images must be managed separately from app releases.
Avoid opportunistic major upgrades such as Postgres `15 -> 16` during an app
release.

## Migration And Backfill Rules

Application images may contain embedded migrations/backfills. Therefore, a
container update may also be a database schema/data update.

Before update, classify pending migrations:

- additive/index-only changes: usually lower rollback risk
- new nullable columns/tables: usually moderate rollback risk
- destructive drops, type changes, data rewrites, reverse migrations: high risk

If rollback may require database downgrade, destructive data changes, or reverse
migrations, stop and document the risk before rolling back.

A container rollback is safe only when the old application can run against the
current post-migration database schema and data.

## Rollback Record

Every update record must include rollback information:

- previous image digest
- previous Git tag/commit when known
- previous latest migration/backfill state
- whether database state changed during the update
- whether rollback is app-only or requires database action
- health verification after rollback, if rollback is performed

Rollback should use the exact previous digest. Do not pull `latest` or deploy a
newer build while performing a rollback.

## Release Command Examples

Create an annotated release tag and push it:

```sh
git tag -a v1.2.3 -m "Release v1.2.3"
git push origin v1.2.3
```

For a release candidate:

```sh
git tag -a v1.3.0-rc.1 -m "Release v1.3.0-rc.1"
git push origin v1.3.0-rc.1
```

The tag push triggers the release workflow. The resulting image digest and build
record are the source of truth for production deployment.

## Version Identity Checklist

A deployed version is fully identified only when all of these are known:

```text
Git tag
Git commit SHA
image digest
database migration version
database backfill version
```

If any item is missing, treat the deployment as only partially traceable.
